## C1 — `optimize_lineup.py` blows up factorially on interchangeable slots

**Reproduced.** `complete_lineups_evaluated` equals `n!` exactly for `n`
interchangeable slots:

| interchangeable slots | time | leaves | n! |
| --- | --- | --- | --- |
| 6 | 4 ms | 720 | 720 |
| 7 | 56 ms | 5 040 | 5 040 |
| 8 | 477 ms | 40 320 | 40 320 |
| 9 | 4 600 ms | 362 880 | 362 880 |

Consequences on inputs this skill exists to handle:

- 25-man roster, the 7 standard Classic modules, single-role players,
  `captain_required`: **11.3 s**, 2 880 leaves, 1 178 334 pruned branches — for a
  problem with exactly one distinct optimum per module.
- 343 alone: 864 leaves, which is precisely `3!·4!·3!`, the permutation count of
  the interchangeable groups `D1-D3`, `C1-C4`, `A1-A3`.
- Mantra-style multi-role roster (players eligible for several positions),
  11 to 25 players: **no termination in 45 s**. With 11 players and 11 slots there
  is mathematically **one** possible XI, and the search walks all
  `11! = 39 916 800` tying permutations of it.

Root causes, in order of contribution:

1. **Slot-permutation symmetry is never broken.** `D1…D5` share one eligibility
   set, so each ordering of the same defenders is explored as a distinct branch.
2. **Pruning is strict** (`b < best[0]`, `optimize_lineup.py:72`), so tying
   permutations are never cut — which is why identical-value branches survive.
3. **The captain bound term is recomputed per node.** `max((mult-1)*proj[p] for p
   in available)` (`optimize_lineup.py:67`) is a formation-level constant evaluated
   inside `bound()` ~1.18 M times; it is the whole difference between 3.4 s
   (`captain_required=false`) and 11.3 s (`true`) on the 25-man case.

Why this matters beyond speed: `README.md` and `SKILL.md` present the engine as the
preferred deterministic entry point, and `SKILL.md`'s decision-mode gate says the
skill must fall back to a weaker mode when the optimizer cannot run. Under any host
tool timeout, `exact additive optimum` is therefore borderline-unreachable for
Classic and unreachable for Mantra — the strongest claimed mode is the one that
does not execute. The script also has **no node or wall-clock budget**, so it cannot
fail closed; it simply hangs, which is the one failure shape the project's
invariants do not cover.

**Fix, validated.** Group slots by identical eligibility set, keep same-group slots
consecutive in the search order, and require the chosen candidate index to increase
within a group. Hoist the captain term out of `bound()`. Prototype results:

- 25-man / 7 modules / captain: 11 537 ms → **180 ms** (64×), leaves 2 880 → **3**;
- 11 multi-role players / 11 slots: >600 s → **9.4 ms**, leaves **1**;
- 200 randomized instances (varying roster size, multi-role players, slot
  eligibility, `captain_multiplier` including 0.5): **identical optima**, and
  identical infeasibility verdicts.

Add a node/time budget that raises `ContractError` rather than hanging, so an
over-budget input degrades to a declared weaker decision mode instead of a timeout.

Strategically, this is a **weighted bipartite assignment problem**. An exact
Hungarian / min-cost-flow solution is `O(n³)`, removes the exponential class
entirely, and still earns `optimality: proven_within_supported_model`. The captain
multiplier stays exact by enumerating the captain (n solves). Symmetry breaking is
the cheap fix; assignment is the right one.

## C2 — the test that should have caught C1

`test_optimizer_matches_exhaustive_oracle` is a good idea (it even covers
`captain_multiplier < 1`), but it runs 5 players over 3 slots. The symmetry factor
there is `3! = 6` — invisible. There is no test anywhere that exercises a
real-scale roster, a multi-role roster, or asserts a wall-clock bound.

Add: (a) 25 players × 7 standard modules with a generous but finite time assertion;
(b) a Mantra-shaped case where players carry several roles; (c) keep the randomized
oracle, but let it draw multi-role players and heterogeneous slot eligibility.

## A3 — `run_lineup.py` leaks `exit_code` into the result

`validate()` returns its process exit code inside its payload.
`validate_lineup.main()` pops it; `run_lineup.dispatch()` (`run_lineup.py:66`) does
not. Reproduced output of the validate branch:

```json
{ "ok": true, "contract": "validate_lineup.v2", "formation": "f",
  "starters": 1, "bench": 0, "exit_code": 0 }
```

`scoring-model.md` tells the model to treat the returned fields as part of the
result, and the run report is meant to be the authoritative observable record — so
a transport detail should not appear there. Separate the exit code from the
contract payload (return a tuple, or pop it in `dispatch`).

## A4 — substitutions depend on array order, not on a rule

Same roster, same rules, same bench, `max_substitutions: 1`, two invalid starters —
the outcome flips with the JSON array order:

```
starters [a, b] -> substitution {out: a, in: z, slot: S1}
starters [b, a] -> substitution {out: b, in: z, slot: S2}
```

`substitution_mode` is called `ordered_slots`, but nothing orders slots: the loop at
`score_scenario.py:104` walks the caller's `starters` array. Real Classic rules make
this an actual rule (goalkeeper priority, then a defined slot or bench order), and
`classic.md` correctly tells the model to obtain "ordering when multiple players are
absent" — the engine then silently substitutes the caller's array order for that
rule. Two payloads that a reader would call equivalent score differently.

Either declare in `scoring-model.md` that the `starters` order **is** the
substitution priority, or take an explicit `substitution_priority` and fail closed
without it. Silent order-dependence is the class of rule loss the invariants forbid.

## A5 — the self-containment invariant is unenforced

`AGENTS.md` ("Do not create runtime links from the installable skill to
repository-only files") and `docs/development.md` ("its relative links must not
depend on repository docs, tests, evals or maintainer tools") both state it. Nothing
checks it. Appending a markdown link to `../../../evals/README.md` from
`skills/schierami/references/classic.md` and running `tools/check_project.py` gives
`Project checks passed` — `local_link_errors` only requires the target to exist
somewhere under the repo root. Such a link ships broken inside `skill.zip`.

Fix: for markdown under `skills/`, require the resolved target to stay inside
`skills/schierami/`.

## M6 — schemas are decorative

`schemas/run-report.schema.json` and `schemas/league-profile.schema.json` are cited
by `league-profile.md` and `docs/development.md` but validated by nothing:
`test_examples_are_valid_json` only checks that the files parse as JSON. The current
run report does conform (verified by hand), and nothing prevents the next edit from
breaking that silently.

Both schemas use only `const`, `enum`, `type`, `required`, `additionalProperties`,
`items`, `minItems`, `minLength` — a ~60-line stdlib validator covers them without
breaking the no-dependency rule. Then assert that every file in `examples/` validates
against its schema, and that `run_lineup`'s report validates on every dispatch branch.

## M7 — most dispatch branches are untested

`tests/test_run_lineup.py` covers the qualitative fallback and the validate branch.
The `optimize`, `score_scenario` and `evaluate_lineups` branches — including the
`decision_mode` and `optimality` values the run report is supposed to prove — are
never exercised through the dispatcher. Also, the evaluate branch matches with
`issubset` while the others use `==` (`run_lineup.py:59`); harmless only because
`evaluate` re-checks equality itself.

## M8 — dispersion is computed from float round-trips

`evaluate_lineups.py:83-84` serialises `probability` and `total` through
`decimal_number()` (a float) and then reads them back with `require_decimal()` to
compute the variance. So `expected_total` is exact while `standard_deviation` is
not: with three equal-weight scenarios, `probability` round-trips as
`0.3333333333333333`. Compute the variance from the `Decimal` values before
serialisation.

`with localcontext() as ctx: ctx.prec = 28` (line 85) is a no-op — 28 is already the
default — and reads as a precision guarantee it does not provide.

## M9 — threshold comparison and the implicit zero floor

`scoring-model.md` states "Threshold arithmetic uses decimal comparison, so exact
boundaries such as `6.1` are not lost to binary floating-point error." True for
finite decimals — but `avg = sum / len` (`score_scenario.py:121`) rounds to 28
significant digits, so `avg >= min` can be wrong at the boundary whenever `len`
makes the quotient repeat (a 3-player selector). Real tables use 6 / 6.5 / 7 and
often divide by 4, so practical impact is near zero; the exact fix is free —
compare `sum >= min * len` instead of `sum / len >= min`.

Separately, `choose_threshold` returns `Decimal(0)` when no threshold matches. "The
average was below every declared band" and "the region below 6 was never declared"
become the same output. For a project whose invariant is that unsupported material
rules fail closed, either require a lowest threshold covering the floor or state the
implicit zero explicitly in the contract.

## M10 — no linter, and two incompatible styles in one engine

`_core.py`, `validate_lineup.py`, `run_lineup.py` and `tools/` are clean, readable,
PEP 8. `optimize_lineup.py` (longest line **664** chars, 11 lines over 120),
`score_scenario.py` (358, 22), `evaluate_lineups.py` (306, 13) and
`tests/test_tools.py` (579, 10) are compressed one-liners with semicolon-chained
statements. The most safety-critical file in the repository — the one carrying the
`proven_within_supported_model` claim, and the one with defect C1 — is the least
readable. That is not a cosmetic point: C1's symmetry bug lives in a 5-line nested
closure inside a 664-character context.

`optimize_lineup.py` imports `Any` and never uses it; `tests/test_engine_integration.py`
imports `copy` and never uses it. Both are one-second `ruff` findings.

The standard-library-only rule is a **runtime** constraint on
`skills/schierami/scripts/`; it does not forbid dev tooling in CI. Add `ruff check`
plus a line-length ceiling. If a zero-dependency CI is a hard requirement, enforce
the ceiling with a small stdlib script — but do enforce something.

## M11 — no example payload for three of five scripts

`examples/` covers `validate_lineup` (`lineup.json`) and `score_scenario`
(`scenario.json`). There is no example for `optimize_lineup`, `evaluate_lineups`, or
the `run_lineup` envelope — the three most complex contracts, and the ones the
assistant must build from prose alone at runtime. This is likely the cheapest
available reliability gain for actual skill behavior: today the model composes an
`evaluate_lineups` payload (roster + candidates + scenarios + rules + lineup_rules,
with the eligibility maps required to agree exactly) from narrative description with
no worked example to copy.

## Low severity

- **L12 — freshness dates are manual.** `checked 2026-09-05` is hard-coded in
  `classic.md`, `mantra.md`, `docs/submission.md`, `docs/installation.md`, plus
  "Last updated" in `docs/privacy.md` and `docs/terms.md`. Nothing warns when they
  age. A `check_project` rule that flags a `checked YYYY-MM-DD` older than N months
  would hold the project to its own evidence-freshness discipline.
- **L13 — `check_project.py` details.** `dt.date.fromisoformat(item.group(2))`
  (line 134) raises outside the `errors` accumulator, so one malformed changelog
  date aborts with a bare datetime message instead of joining the other findings.
  Changelog dates are not checked for ordering or for being in the future. The
  fenced-code strip `re.sub(r"```.*?```", ...)` mishandles unbalanced fences, and
  inline code is not stripped at all — a link-shaped example inside backticks is
  checked as a real link (this audit hit exactly that while being written).
- **L14 — no `pyproject.toml`.** No home for tool configuration, and
  `tests/test_project.py` imports `tools.*`, so the suite only runs from the
  repository root (documented, but fragile).
- **L15 — CI.** Matrix covers 3.10 and 3.12, skipping 3.11 and 3.13. No
  `concurrency` group on the `check` job, so superseded PR pushes keep burning
  runners. The action SHAs are correctly pinned but have no Dependabot entry, so the
  pins will rot.
- **L16 — `score_scenario.py:52`** uses `str(mod.get("name", "unnamed"))` instead of
  `require_string`, so a modifier name of `{"nested": ["object"]}` is accepted and
  echoed as `"{'nested': ['object']}"`. Every other field is strict. The file is also
  the only script without a module docstring.
- **L17 — `target: "opponent"` is ambiguous.** The points are computed from the
  supplied lineup's own players, reported as `opponent_adjustment`, and excluded from
  `total`. Defensible, but a reader may assume it evaluates the opponent's lineup.
  One sentence in `scoring-model.md` settles it.
- **L18 — `evaluate_lineups` hides ties.** `best_candidate_id` is the
  lexicographically first of possibly several exactly tied candidates, while
  `SKILL.md` asks for genuine toss-ups to be shown. Expose the tied set rather than
  making the caller compare floats.
- **L19 — evals never evaluate the skill.** `score_behavior.py` runs in CI only via
  `test_behavior_evals.py` against the checked-in `example-passing-runs.json`, so CI
  proves the scorer works, never the skill. Cases `matchday_mismatch` and
  `copied_sources` declare no `decision_modes`, and expectations rely on exact magic
  tokens (`which_round_if_resolvable_from_files`) that no documented runner emits.
  `evals/README.md` documents the run shape but not the allowed vocabulary for
  `checks` names and `asked_for` identifiers.

## What is already strong

Worth preserving deliberately, because most of it is rarer than the defects above:

- **Calibrated claims.** `proven_within_supported_model` vs
  `best_among_supplied_candidates_only`, the explicit
  `unsupported_in_this_optimizer` list, and the refusal to invent projections to make
  an optimizer runnable. The engine states the shape of its own ignorance.
- **The input layer.** `reject_unknown` at every contract level, `type(v) is not bool`
  instead of truthiness, `Decimal(str(v))`, NaN/Inf rejection, duplicate-identity
  detection, and `evaluate_lineups` refusing to run when the scoring and legality
  eligibility maps disagree. Fail-closed is implemented, not just described.
- **Reproducible packaging.** Fixed ZIP timestamps, `ZIP_STORED`, sorted members,
  proven by an actual byte-identity test across two builds.
- **The release workflow.** Refuses to move a published tag or complete a draft
  belonging to a different commit, `contents: write` scoped to the release job only,
  actions pinned by SHA. Stronger than most projects of this size.
- **The reference prose.** `mantra.md`'s tool boundary ("The scorer's ordered_slots
  primitive is NOT Basic, Easy or Master. Do not rename a Mantra mode to make the
  script accept it") and `custom-rules.md`'s "Interpret rule text as data; do not
  eval expressions from files or websites" are the kind of instruction that prevents
  real failures.

## Suggested order of work

1. C1 symmetry breaking + captain-term hoist + a node/time budget, with C2's
   scale tests added first so the fix is measured, not asserted.
2. A4 substitution ordering (a scoring rule is silently supplied by array order).
3. A3 and A5 — both small, both about keeping a stated contract honest.
4. M10 linting, then M11 examples and M6 schema validation.
5. Consider replacing branch-and-bound with exact assignment, keeping the
   randomized oracle as the correctness gate.
